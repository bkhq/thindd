# ADR: Use `SEEK_HOLE`/`SEEK_DATA` for hole detection, not `FIEMAP`

Status : Accepted
Date   : 2026-08-19
Sunset : revisit if a target file system is found where `SEEK_HOLE` is materially worse
Owner  : thindd maintainers

## Context

Upstream `bmaptool` prefers the `FIEMAP` ioctl and falls back to
`SEEK_HOLE`/`SEEK_DATA`. `FIEMAP` returns the extent list in one call, which is
cheaper on a heavily fragmented image, and it reports extent flags that
`SEEK_HOLE` cannot express.

Against that:

* `FIEMAP` needs a raw `ioctl`. Neither `rustix` nor `nix` can express it
  without `unsafe`, which would mean relaxing Hard Lock 3 for the one module
  that calls it.
* `FIEMAP` reports speculative preallocation (`FIEMAP_EXTENT_UNWRITTEN` and, on
  some file systems, plain delayed allocation) as extents, so it can *over*-map
  relative to `SEEK_HOLE`.
* This tool scans content for zeroes anyway. Any block `SEEK_HOLE` calls "data"
  but which is in fact zero is caught by the scan, so the two signals overlap
  precisely where `FIEMAP` would have helped.

## Decision

Use `SEEK_HOLE`/`SEEK_DATA` only, via `rustix::fs::seek`. When the kernel or
file system reports the operation as unsupported, treat the whole image as
mapped and let the zero scan do the work — the safe direction to be wrong in.

## Consequences

* Both crates keep `#![forbid(unsafe_code)]`.
* Hole discovery costs two `lseek` calls per extent instead of one ioctl per
  batch of extents. On an image with thousands of extents this is measurable but
  small, and it happens once per run.
* `--detect holes` may map slightly *more* than upstream on file systems where
  `SEEK_HOLE` is coarser than `FIEMAP`. With the default `--detect both` the
  difference disappears.
